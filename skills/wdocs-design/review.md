# wdocs-design 리뷰

참고: refactoringenglish.com "Useful feedback on design docs", "How to Write an Effective Software Design Document"

리뷰의 목적은 네 가지다. 설계 결함을 일찍 찾는다. 관련된 사람들이 같은 그림을 본다. 리뷰가 작은 다툼으로 멈추지 않게 한다. 리뷰어의 시간을 설명 찾기가 아니라 설계 판단에 쓰게 한다.

순서는 에이전트 리뷰 → 첫 리뷰어 한 명 → 전체 리뷰 → 남은 이슈 회의 → (구현 뒤) 설계 회고다.

## 1. 에이전트 리뷰

문서를 쓴 에이전트가 아닌 새 에이전트에게 맡긴다. 쓴 사람은 자기 문서의 빈칸을 잘 못 본다. 세 리뷰는 서로 기다릴 필요가 없으니 동시에 돌린다(원문이 없으면 두 가지). 지시문의 `<...>`만 채워서 그대로 쓴다.

결과가 오면 지적마다 원문이나 코드에서 직접 확인한 뒤 고친다. 설명이 부족한 지적은 설명을 고치고, 설계에 대한 이견은 Open issues 블록으로 만든다. 확인되지 않은 지적은 고치지 않고 사용자에게 보고한다. 고친 뒤 마무리 점검 1~3을 다시 돌린다.

### PRD 대조 지시문

PRD(또는 맥락 절에 적은 요구)를 원문으로 넣는다. 원문이 없으면 이 리뷰는 건너뛰고 사용자가 대조한다.

```
읽기 전용 검증 작업이다. 파일을 수정하지 말고 .env 파일은 읽지 마라. 한국어로 답하라.

요구사항 원문: <원문 파일 경로들. PDF면 pdftotext -layout으로 뽑은 텍스트 경로>
검증 대상: <문서 경로>
문서의 우선순위 규칙: <문서 정보에 적은 규칙>

원문에서 요구사항, 정책, 예외, 성공 지표를 직접 하나씩 열거해서, 설계가 그것을 맡는지 대조하라.
문서가 뽑아 둔 목록을 기준으로 삼지 마라.

출력(1200단어 이내):
1. 누락: 원문 요구 중 설계가 맡지 않는 것. 원문 인용과 줄 번호
2. 불일치: 원문과 다르게 설계한 것
3. 원문끼리(또는 한 원문 안에서) 다른데 Open issues에 없는 것
4. 설계가 원문에 없는 요구를 새로 만든 것
확실하지 않으면 "불확실"과 이유. 글자가 깨져 판단 못 한 부분은 따로 목록. 문제가 없는 번호는 "없음".
```

### 문서 안 일관성 지시문

```
읽기 전용 리뷰다. 파일을 수정하지 말고 .env 파일은 읽지 마라. 한국어로 답하라.

리뷰 대상: <문서 경로>
문서의 우선순위 규칙: <문서 정보에 적은 규칙>

문서 안에서 서로 맞지 않는 곳을 찾아라.
- 같은 사실이 절마다 다르게 적힌 곳(시나리오, 사용자 역할, 화면, 아키텍처, 구현 일정, 부록 사이)
- 본문 숫자(몇 곳, 몇 개, 몇 건, 몇 가지)가 표의 행 수나 실제 개수와 맞는지
- 시나리오나 완료 조건의 기대 건수가 문서의 규칙대로 계산한 값과 맞는지(알림 건수, 이력 건수)
- 설계와 구현 일정에 나온 API가 부록 명세에 모두 있는지, 명세에만 있고 작업에 없는 것은 없는지
- 선행 작업이 같은 Milestone이나 앞 Milestone에 있는지, 테스트에 필요한 작업이 선행 작업에 빠지지 않았는지
- Open issues 블록마다 Next step이 있는지
- Open issues의 Proposal이 본문에 그대로 반영됐는지(Proposal대로 개발한다고 했는데 표나 작업에 빠진 것)
- Proposal이 문서 정보의 우선순위 규칙과 맞는지, 벗어나면 Background에 이유가 있는지
- 본문에 출처나 해석 설명("PRD에 따라", "~로 본다")이 줄마다 붙어 있지 않은지, PRD 내용을 다시 옮겨 적지 않았는지, Open issues에 작성자가 정할 수 있는 작은 차이가 올라가 있지 않은지
- 상태, 값, 분류의 정의가 모든 경우를 덮는지(어느 행에도 들어가지 않는 경우)
- 이름으로 가리킨 절이나 표가 실제로 있는지
- Open issues 블록의 Affects에 적힌 절에 Proposal이 그대로 적혀 있는지, 본문에 이슈 표시가 남아 있지 않은지

출력(1000단어 이내): 심각한 것부터. 문제마다 "절 번호와 제목 / 문서 문구 인용 / 무엇이 문제인지 / 고치는 방법 한 줄".
문제가 없으면 없다고 적어라.
```

### 읽는 사람 지시문

리뷰어가 찾아보거나 짐작하지 않아도 되는지 본다. 첫 리뷰는 설계가 아니라 설명을 고친다.

```
읽기 전용 리뷰다. 파일을 수정하지 말고 .env 파일은 읽지 마라. 한국어로 답하라.

리뷰 대상: <문서 경로>
너는 <읽는 사람. 예: 이 설계의 API를 쓸 프론트엔드 개발자. 백엔드 코드는 모른다>다.
문서 정보부터 설계까지와 너에게 필요한 부록만 처음부터 읽어라. 링크된 PRD는 필요할 때만 열어라. 다른 자료는 찾아보지 마라.

읽으면서 아래를 적어라.
- 처음 나왔는데 설명이 없는 말(용어, 약어, 내부 이름)
- 다른 절을 읽어야만 이해되는 곳
- 무엇을 해야 하는지(무엇을 만들고, 무엇을 결정해야 하는지) 알 수 없는 곳
- 같은 것을 다른 이름으로 부르는 곳
- 너에게 해당하는 절인데 필요 없는 세부라서 건너뛰고 싶었던 곳
- 다 읽은 뒤 남은 질문

출력(800단어 이내): 위치(절 번호와 제목) / 인용 / 무엇이 막혔는지 / 고치는 방법 한 줄. 설계에 대한 의견은 맨 끝에 따로 적어라.
```

## 2. 사람 리뷰

1. 첫 리뷰어 한 명. 이해관계가 가장 큰 사람(구현자, 이 기능을 쓰는 쪽, 연결된 시스템 담당자)에게 먼저 보낸다. 여러 명에게 한꺼번에 보내면 서로 누가 꼼꼼히 볼 거라고 생각하고 넘긴다. 이 단계에서는 설명을 고친다. 이견이 없는 지적은 바로 반영하고, 설계에 대한 이견은 Open issues 블록으로 만든다.
2. 전체 리뷰. 문서 정보의 상태를 In review로 바꾸고 리뷰어와 리뷰 기한을 적는다. 기한은 최소 2 영업일이고 일이 많은 시기면 더 준다. 공유할 때 리뷰어마다 볼 절을 메시지에 적는다.
3. 문서로 답한다. 질문이나 오해는 댓글이나 메신저로 설명하지 않고 문서를 고친다. 다른 사람도 같은 곳에서 헷갈린다. 말로 먼저 설명했으면 문서를 고친 뒤 그 사람에게 문구가 맞는지 확인받는다. 리뷰어가 지난번 이후 바뀐 것을 볼 수 있게, 고친 뒤 문서 공유 도구의 버전 비교를 쓰라고 알린다.
4. 댓글 스레드는 끝까지 닫는다. 고쳤으면 답하고 닫는다. 고쳤는지 확실하지 않으면 리뷰어에게 묻고, 며칠 답이 없으면 닫는다. 두세 번 오가도 정리되지 않으면 Open issues 블록으로 옮기고, 양쪽 관점을 같은 무게로 적고, 블록의 Affects에 그 절을 적고, 스레드에는 옮겼다고 남기고 닫는다.
5. 결정되면 블록의 Decision을 먼저 채우고, 결정이 Proposal과 다르면 Affects의 절을 고치고, 블록을 Closed issues로 옮긴다.
6. 회의는 마지막에 한다. 글로 정리되지 않은 Open issues만 안건으로 삼고, 안건(Issue 번호와 제목)을 미리 공유하고, 이미 결정된 것은 다시 다루지 않는다고 적는다.
7. 모든 Open issues가 닫히면 상태를 Approved로 바꾼다.

## 3. 설계 회고 (구현 뒤)

사람이 아니라 진행 방식을 본다. "누가 왜 잊었나"가 아니라 "사람의 기억에 기대지 않으려면 진행 방식을 어떻게 바꿀까"를 묻는다.

1. 작성자가 먼저 잘 된 것과 안 된 것을 적는다.
2. 참여자에게 아래 질문을 보낸다. 작성자도 먼저 답한다.
   - 예상보다 오래 걸린 작업은 무엇이고 왜인가
   - 예상과 다르게 동작한 의존 시스템이나 기존 코드는 무엇인가
   - 설계 때 놓친 것은 무엇이고, 어떤 진행 방식이면 덜 놓쳤을까
   - 순조로웠던 작업은 무엇이고, 설계 과정의 어떤 점이 도왔나
3. 답을 모아 자주 나온 것, 큰 것부터 정리해 공유하고 회의에서 진행 방식 개선안을 정한다.
4. 개선안 중 문서 작성 방식에 관한 것은 이 skill에 반영한다.
