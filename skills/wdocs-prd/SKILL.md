# wdocs-prd: PRD

PRD는 「무엇을, 왜」를 정한다. 기술 결정(구성, 데이터 모델, API)은 정하지 않는다. 그것은 `wdocs-design`의 몫이다. 두 문서는 서로 링크만 걸고 내용을 반복하지 않는다. 쓰기 전에 `../../shared/style.md`를 읽는다.

참고: Figma PRD(문제 정렬, 해법 정렬, 출시 준비), Kevin Yien PRD(하지 않는 것), Design Docs at Google(목표와 하지 않는 것의 구분).

## 쓰기 전

- 이 일이 PoC를 거쳤으면 PoC 문서의 판정과 측정값을 확인한다. 문제 절에 링크한다.
- 화면 디자인이 있는지 확인한다. 있으면 화면 그림은 디자인을 잘라 쓰고, 없으면 작성자가 와이어프레임을 그리고 문서 정보에 "디자인: 없음"을 적는다.
- 요구가 대화로만 있으면 시나리오, 목표, 하지 않는 것을 짧게 정리해 사용자에게 확인받고 쓴다.

## 구조

큰 제목은 `## 1. 문서 정보`처럼 번호를 붙인다. 내용이 없는 절은 지우고 번호를 다시 매긴다. 맨 앞 세 절(문서 정보, 요약, 문제)만 읽어도 무엇을 왜 하는지 알게 쓴다.

| 절 | 내용 |
|---|---|
| 문서 정보 | 작성자, 상태(Draft, In review, Approved), 작성일, 리뷰어, 근거 문서(PoC, 디자인, 요청), 이어지는 Design Doc 링크 |
| 요약 | 다섯 줄 이내. 누구의 무슨 문제를 무엇으로 푸는지 |
| 문제 | 지금 동작과 그 때문에 생기는 문제. 확인한 사실만. PoC 판정과 측정값 |
| 목표 | 구현이 아니라 결과로 쓴다("취소 사유 컬럼 추가"가 아니라 "고객이 운영자 연락 없이 주문을 취소한다") |
| 하지 않는 것 | 할 만해 보이지만 이번에 하지 않는 것과 이유. "죽지 않는다" 같은 부정형 목표는 쓰지 않는다 |
| 성공 지표 | 지표, 재는 법, 목표값. 잴 수 없으면 대신 재는 기록 |
| 용어 | 읽는 사람이 모를 말(있을 때만). 요구 원문의 용어가 화면 표기와 다르면 둘을 함께 적는다 |
| 사용자 역할 | 역할 x 동작 표. 역할 이름으로 쓴다(고객, 운영자, 판매자 관리자). "작성자"처럼 여러 역할로 읽히는 말은 쓰지 않는다 |
| 시나리오 | 이름 붙인 흐름마다 번호 단계. 첫 단계에 누가 어느 화면에서 하는지 |
| 화면 | 화면마다 작은 제목과 그림 하나, 그 아래 사용자가 보고 하는 일. 그림과 글이 다르면 글을 따른다고 절 첫머리에 적는다 |
| 정책과 예외 | 규칙 표, 예외 상황과 처리 |
| 기존 동작 변경 | 지금, 바뀐 뒤, 영향 받는 사람(있을 때만) |
| 이번에 빠지는 기능 | 목록과 이유 |
| 출시 준비 | 출시 전에 확인할 것 체크리스트(법무, 고객 안내, 운영 교육, 데이터 이전) |
| Open issues | 기획이 정해야 할 것만 |
| Closed issues | 결정된 이슈 |
| 부록 | 화면 상태별 문구, 긴 표 |

화면 문구는 제품 언어 그대로 쓴다. 디자인이 없으면 작성자가 문구를 정한다.

## 와이어프레임

디자인이 없을 때 SVG로 배치만 그린다. 문서마다 모양이 같게 한다.
- 캔버스 1200 x 760, 바탕 흰색, 선 `#c1c7d0` 1px, 글자 `#172b4d`.
- 왼쪽 사이드바 너비 220, 바탕 `#f4f5f7`, 메뉴 4~6개, 지금 화면 메뉴는 굵게.
- 본문 왼쪽 위 화면 제목(24px, 굵게), 아래 설명 한 줄(14px, `#6b778c`).
- 표는 헤더 행(`#f4f5f7`)과 데이터 3~4행. 버튼은 모서리 6, 주 버튼은 `#0c66e4` 바탕에 흰 글자.
- 이 문서에서 새로 생기거나 바뀌는 부분만 `#de350b` 2px 테두리.
- 파일 이름 `images/screen-<이름>.svg`, PNG로 만들어 열어 본다.

## Open issues 형식

```
### Issue 2. 판매자 관리자가 이미 발송된 주문의 취소를 승인할 수 있는가

Decision:

Affects: 사용자 역할, 정책과 예외

Background:
- 요청 문서는 ...
- 디자인은 ...

Options:
- A. ...
- B. ...

Proposal: A. 이유 한 줄

Next step: 다음 리뷰에서 기획이 정한다.
```

- Open issues 첫 줄에 "아래 항목은 본문에 Proposal대로 적혀 있고, 확인 전까지 그대로 진행한다"를 적는다.
- 본문에는 Proposal을 결정처럼 쓰고 이슈 번호를 붙이지 않는다. 이슈에서 본문으로는 Affects로 찾아간다.
- 작성자가 정할 수 있는 작은 차이는 올리지 않고 본문에 결정으로 쓴다.
- 결정되면 Decision을 먼저 채우고, Proposal과 다르면 Affects의 절을 고치고, Closed issues로 옮긴다.
- 영어로 두는 것은 Open issues, Closed issues 제목과 라벨(Decision, Affects, Background, Options, Proposal, Next step)뿐이다.

## 넘길 때

- 문서 공유 도구에 올리는 것은 사용자가 한다. 그림 파일 목록을 "파일 / 들어갈 절" 표로 준다.
- 요구가 확정되면 `wdocs-design`으로 Design Doc을 쓴다. PRD 문서 정보에 그 링크를 넣는다.

## 점검

`python3 ../../shared/check_style.py --kind prd <문서>`
